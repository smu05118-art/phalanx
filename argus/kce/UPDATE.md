# 한국건설 (argus/kce) — 데이터 자체 갱신 로직

> 원 사이트는 외부(encprojects) 빌더가 만든 산출물이다. 이 문서는 **그 빌더 없이 우리가 DART에서 직접**
> 데이터를 갱신하기 위한 설계·구현 사양이다. 데이터 계약과 페이지 로직은 [LOGIC.md](LOGIC.md) 참조.
> 구현: `tools/kce_lib.py` `tools/kce_parse.py` `tools/kce_fetch.py` `tools/kce_build.py`, 테스트 `tools/tests/`.

## 0. 요약 — 무엇을, 어디서, 어떻게

갱신 단위는 **회사 × 분기**다. 한 분기의 정기보고서 하나에서 II-4·III-8·(XI절)을 뽑아
해당 분기 슬롯(`fq`의 인덱스)을 채우고, 파생값을 재계산한다.

```
kce_fetch.py  →  raw/<co>_{ii4,ii4x,p8}.html      (DART viewer.do 절 HTML)
kce_parse.py  →  표 → 레코드 리스트                (머리행 정규화 + 별칭 매핑)
kce_build.py  →  index.html의 const DATA 갱신      (매칭·반영·재집계·예측·검증)
```

| DATA 필드 | 원천 | 주기 | 구현 상태 |
|---|---|---|---|
| `s.amt/cmp/bal/pr` | 정기보고서 II-4 수주상황(또는 XII 상세표) | 분기 | ✅ 구현·검증 |
| `sFilled`(실측 표시) | 위와 동일 | 분기 | ✅ |
| `sFilled='p8'` 백필 | II-4에서 빠진 사업장을 III-8로 역채움 | 분기 | ✅ (§3.5) |
| `ev`·`names` (변경 이력) | II-4 전분기 대조 | 분기 | ✅ |
| `p8`(III-8 연결/별도) | 정기보고서 III-8 「진행률적용 수주계약 현황」 | 분기 | ✅ |
| `rev.diff/src/filled` | `cmp` 증분 계산 | 분기 | ✅ |
| `summary`·`revSummary` | 사이트 재집계 | 분기 | ✅ (`src` 규칙별 분기 — §3.6) |

| `sFilled='fcst'` 미래 4분기 | S-curve 리베이스 | 분기 | ⚠️ 구현했으나 **기본 비활성** (§3.7) |
| `xip`/`xipFull` (XI-1) | 정기보고서 XI절 + 수시공시 | 반기 | ⏳ 사양 확정, 미구현 (§6) |
| `coRev` (실제 매출) | II-4 매출실적표 + 손익계산서 누적차분 | 분기 | ⏳ 사양 확정, 미구현 (§5) |
| `prC`/`prCv` (기준 공정률) | S-curve 재적합 후 리베이스 | 분기 | ⏳ 미구현 (곡선은 `assets/curve_D.json`에 보존) |
| `interp`/`bcst` 보전 | 결측 구간 보간·역산 | 분기 | ⏳ 미구현 |
| `backtest`·`curve`·`headers` | 재계산·재적합 필요 | 분기 | ⏳ 미구현 (§7 스테일 경고) |

**검증된 충실도**: 2026Q2를 원문에서 다시 빌드해 임베드 DATA와 **전필드 대조**한 결과
**5사(현대건설·삼성E&A·대우건설·DL이앤씨·HDC현산)가 차이 0**(완전 재현)이고, 삼성물산 2셀·GS건설 6셀만 남는다.
둘 다 우리 로직 결함이 아니다 — 내역은 §9, 미해결 한계는 §10.

측정 시 주의: "불일치 건수"만 보면 안 된다 — 빌더가 **아무것도 쓰지 않아도** 불일치는 0이 되고,
`summary.total`은 법인 간 재배분에서 보존되므로 총계 일치도 근거가 못 된다. 실제로 단위 버그로
값을 1/100로 기입하던 시점에 삼성E&A가 가장 깨끗한 리포트를 냈다. 그래서 테스트는 전필드 대조와
새 분기 적재 경로(§8)를 함께 본다.

## 1. 수집 (`kce_fetch.py`) — DART 무키 3단 경로

OpenDART API 키 없이 공개 웹 엔드포인트만으로 절 단위 정밀 추출이 된다(전 경로 실호출 검증).

### 1.1 3단 경로

```
① 검색   POST https://dart.fss.or.kr/dsab007/detailSearch.ax
          textCrpNm=<회사명>&startDate=&endDate=&publicType=<A001|A002|A003|I001>
          → 응답 HTML에서 main.do?rcpNo=(\d{14}) 정규식으로 접수번호 획득
② 목차   GET  https://dart.fss.or.kr/dsaf001/main.do?rcpNo=<14자리>
          → 인라인 JS의 node['text'|'dcmNo'|'eleId'|'offset'|'length'|'dtd'] 블록 = 절 제목 → 뷰어 파라미터
③ 본문   GET  https://dart.fss.or.kr/report/viewer.do?rcpNo=&dcmNo=&eleId=&offset=&length=&dtd=dart4.xsd
```

`publicType`: `A001` 사업보고서 · `A002` 반기 · `A003` 분기 · `I001` 거래소 수시공시(단일판매ㆍ공급계약).
`report_kind(q)`가 분기 → 보고서 종류를 정한다: Q1·Q3 → 분기(A003), Q2 → 반기(A002), Q4 → 사업(A001).

### 1.2 함정 (전부 실측으로 확인됨)

1. **`eleId`(절 번호)는 회사마다 다르다** — 삼성물산 기타재무=111, 현대건설=91. 하드코딩 불가,
   반드시 목차 `text` 문자열 매칭으로 결정한다(`SECTION_PATTERNS`).
2. **삼성물산형은 II-4 본문에 상세 표가 없다** — "※상세 현황은 '상세표-5' 참조" 한 줄뿐이고
   실데이터는 **XII. 상세표** 절에 있다. 그래서 `ii4`(본문)와 `ii4x`(상세표)를 **둘 다** 받고,
   빌더가 행수가 큰 쪽을 채택한다(원 파서의 "행수 큰 상세표 우선" 규칙과 동일).
3. **거래소 수시공시는 인코딩·파라미터가 다르다** — rcpNo 9~11번째 자리가 `800`이면 거래소공시이고,
   본문은 **EUC-KR**, 뷰어 파라미터는 `eleId=0&offset=0&length=0&dtd=HTML` 고정이다.
4. 정기보고서 본문은 UTF-8. `_decode()`가 rcpNo로 인코딩을 분기한다.
5. 접수 시점: 분기말 +45일(사업보고서 +90일) 안팎. `fetch_quarter`가 분기말 월 1일 ~ +3개월(4Q는 +4개월) 말일로 검색한다.
   **정정보고서**가 나중에 나오면 같은 분기를 다시 돌려 덮어쓴다(재적재는 멱등 — §4.8).

### 1.3 OpenAPI 대안 (키 확보 시)

| 엔드포인트 | 용도 |
|---|---|
| `/api/corpCode.xml` | `corp_code`(8자리) ↔ `stock_code` 매핑. ZIP 응답 |
| `/api/list.json` | 접수번호 목록 — 검색 HTML 파싱보다 안정적(JSON) |
| `/api/document.xml` | 보고서 원문 전체 ZIP — 다만 절 단위가 아니라 전체라 무겁다 |

**수주 표를 직접 주는 API는 없다.** 키가 있어도 본문은 결국 파싱해야 하므로,
목록 발견만 `list.json`으로 대체하고 본문은 `viewer.do` 절 단위를 유지하는 조합을 권장한다.
`kce_fetch.api_list()`가 `DART_API_KEY` 환경변수를 읽어 이 경로를 제공한다.

## 2. 파싱 (`kce_parse.py`) — 머리행 전쟁

원 사이트의 `headers.html`(파서 머리행 지도)은 "회사가 분기마다 열 이름을 바꾸거나 표를 쪼개는 것이
조용한 데이터 손실의 원인"이라고 명시한다. 그 카탈로그에서 역산한 규칙이 아래다.

### 2.1 열명 정규화 `norm_col()`

순서대로: `(단위 : …)` 프리픽스 제거 → `(주1)`·`(%)` 괄호주석 제거 → **모든 공백 제거**(전각 포함)
→ 가운뎃점·슬래시 제거. 실제로 흡수되는 변형(테스트 `test_norm_col_catalog`):

| 원문 | 정규화 | 사례 |
|---|---|---|
| `계약일 (공사착공일)` / `계약일(공사착공일)` | `계약일(공사착공일)` | 대우건설이 4번 개명한 열 |
| `완 공 예 정 일` / `완 공예 정 일` | `완공예정일` | DL건설, 공백 위치까지 이동 |
| `진행률 (%)` / `진행률(%)` | `진행률` | 같은 분기 연결/별도 표기가 다름 |
| `(단위 : 백만원) 신고일자` | `신고일자` | DL이앤씨 2024Q4 캡션 오염 |
| `프로젝트명 (주1)` | `프로젝트명` | DL이앤씨 구 14열 스키마 |
| `판매ㆍ공급금액` / `판매/공급금액` / `판매공급금액` | `판매공급금액` | 회사별 가운뎃점 방언 |

정규화 후 `COL_ALIAS` 사전이 표준 필드로 매핑한다(`공사명`·`품목`·`프로젝트명`·`구분` → `nm`,
`기본도급액`·`수주총액` → `amt`, `계약자산총액` → `ub`, `매출채권총액` → `rc` 등 개념 열 교체까지 흡수).

### 2.2 표 구조 처리

- **다층 헤더 평탄화**: rowspan/colspan을 전개(`_expand_grid`)한 뒤 부모 프리픽스를 결합
  (`판매ㆍ공급금액(백만원) 당기` 형태). 같은 이름 반복은 접지 않는다.
- **`<th>` 없는 머리행**: DART 표 상당수가 `td`만 쓴다. `_looks_header()`가
  "셀이 전부 비수치 + 절반 이상이 헤더 어휘"면 머리행으로 인정(최대 2행).
- **머리행 계승**: `(2) 별도 기준` 표처럼 머리행을 반복하지 않는 관행이 있어,
  헤더 없는 표가 직전 헤더 표와 열 수가 같으면 그 헤더를 물려받는다(`inherited`).
- **중복 필드 우선순위** `_PREF`: 삼성물산 상세표는 `품목`(='건설사업')과 `공사명`이 공존한다 —
  `nm`은 `공사명 > 프로젝트명 > 구분 > 품목` 순으로 채택. `sd`도 동일한 우선순위 목록을 둔다.
- **표 선택은 머리행 완전일치가 아니라 핵심 필드 집합 포함 여부**:
  II-4는 `{nm, amt, cmp, bal}`, III-8은 `{amt, pr, ub, rc}`.
- **`구분` 열이 공사명이 아닐 수 있다**: 삼성E&A 표는 `구분`이 국내관급/국내민간/해외
  3종 분류이고 실제 공사명은 `품목` 열이다. 이름 우선순위만 쓰면 분류 열을 잡으므로,
  `nm` 후보의 **값 고유도**(distinct ratio)가 0.5 미만이면 더 고유한 후보로 교체한다.
- **표 단위가 회사마다 다르다**: 삼성E&A는 **억원**, 나머지는 백만원. 단위 캡션은 본문 텍스트가
  아니라 **별도의 1셀짜리 표**(`<TD align='RIGHT'>(단위 : 백만원)</TD>`)로 들어오므로,
  파서가 셀 3개 이하의 소형 표를 다음 표의 lead 문맥으로 넘겨준다. 환산은 정수배로 처리해
  부동소수점 오차를 만들지 않는다(억원→백만원은 ×100).
- **III-8 연결/별도 판정**: `(1) 연결 기준`·`(2) 별도 기준` **소절 표지를 최우선**으로 본다.
  본문에 "연결회사는 발주처와 협의 중"처럼 서술이 섞여 있어 단순 포함 검사는 오판한다(삼성물산 실사례).
  표가 하나뿐일 때는 단정하지 않는다 — HDC현산은 2023Q4부터 **연결만** 내므로 '별도'로 찍으면 전량 오배정된다.
- **복수 표 수집이 기본** — 현대건설은 법인별 3~4표, GS건설은 관급/민간/해외 6표(2025Q1부터 2표),
  HDC현산은 관급/민간 2표다. 하나만 잡으면 조용히 데이터가 사라진다.
- **미지 헤더는 침묵하지 않는다**: 필드 3개 이상 매칭 + 3행 이상인데 핵심 집합을 못 채우면
  `unknown_headers`로 보고하고, 빌더는 **거기서 중단한다**(fail-closed).

### 2.3 값 파싱 `num_of()`

콤마 제거, `99.00%` → `99`, `(1,000)` → `-1000`, `-`·`–`·빈칸 → `None`.
`USD 2,426,809,931` 같은 외화 표기는 `None`(별도 처리 대상 — XI-1의 `cur` 필드).

## 3. 빌드 (`kce_build.py`) — 분기 슬롯 채우기

`update_quarter(co, q, raw_dir, apply)` 한 함수가 전 과정을 수행한다. `--apply` 없으면 dry-run 리포트만.

### 3.1 분기 슬롯 결정

- `q`가 이미 `fq`에 있으면 그 인덱스에 **재적재**(정정보고서 반영).
- `q`가 `fq[-1]`의 다음 분기면 `_extend_axes()`로 축을 늘린다:
  `fq` +1, `fqF = fq + 미래 4분기`. 기존 모든 시계열 배열(사이트·집계·`prCv[].v` 포함)을
  옛 `fqF` 라벨 기준으로 새 축에 재배열한다(값 이동이 아니라 **라벨 매칭 remap**).
- 그 외 분기는 거부(건너뛴 분기가 있으면 순서대로 돌려야 한다).

### 3.2 사업장 매칭

정규화 공사명으로 인덱스를 만든다 — 현재 `nm` + `names` 이력 전체 + `p8Full.품목` + `xip.nm`.
공사명은 분기마다 흔들리므로(`평택P4Ph2(하층동편)` → `평택 P4 Ph2/3`) 이력 전체가 키가 되어야 한다.

동명이 여럿이면(예: 삼성물산 `평택 P4 Ph2` 2건, 현대건설 `힐스테이트 레이크 송도 4차 (A16)` 2건):
1순위 **직전 실측 도급액과의 근접도**, 2순위 발주처 일치. 발주처 우선으로 하면
연결 종속법인이 같은 이름으로 올린 건과 뒤바뀐다(실제로 겪은 실패 — 현대건설 송도랜드마크시티 사례).

매칭 실패 = 신규 사업장. `<접두>-2-<다음 일련번호>`로 생성하고 `has=[1,0,0]`으로 시작한다.

### 3.3 실측 반영

```
amt, bal ← 원문 그대로
cmp      ← 원문. 원문이 '-'인데 amt·bal이 있으면 0 (미착공 관행 — 대우건설 정비사업 다수로 검증)
pr       ← round(cmp / amt × 100, 2)          (임베드 DATA와 소수 2자리까지 일치 확인)
sFilled[k] ← None (실측)
names    ← 원문 공사명이 직전과 다르면 [q, 원문] 추가
```

### 3.4 변경 이벤트 감지

직전 **실측** 분기와 비교해 `기본도급액`·`공사착공일`·`완공예정일`·`발주처` 변경을 `ev`에 기록
(`{fq, f, o, n, d}`, 금액은 `d`에 차액). 날짜는 `norm_date()`로 정규화하며
`2023년 5월` 형태는 착공=1일·완공=말일 관행을 적용하고, `미정` 같은 비날짜는 **기존값을 유지**한다
(그렇지 않으면 매 분기 가짜 이벤트가 쌓인다 — 대우건설에서 실제로 121건 오탐을 냈던 지점).

### 3.5 III-8 반영

표의 **연결/별도 순서는 회사·분기마다 뒤집힌다**(현대건설은 첫 표가 별도, 삼성물산은 첫 표가 연결).
따라서 lead 문맥의 `(1) 연결 기준`·`(2) 별도 기준` 앵커를 1차로 쓰되,
앵커가 없으면 **직전 분기 `p8[basis]`와의 연속성 점수**로 배정을 정한다.

**별도 = 연결 완전 동일값이면 연결을 저장하지 않는다** — 원 빌더의 중복 제거 규칙이다.
검증: 삼성물산 2026Q2 연결 표 15행 중 별도와 다른 3건만 DATA에 `p8['연결']`로 존재(정확히 재현).

같은 사업장에 같은 basis를 두 번 배정하지 않도록 `used` 집합으로 막고,
수주총액 연속성으로 동명 후보를 고른다(§3.2와 동일 문제).

### 3.6 재집계

```
rev.diff[i] = cmp[i] − cmp[i−1]        (k와 k+1 두 칸을 갱신 — 다음 분기 증분도 바뀐다)
rev.src[i]  = worse(sFilled[i−1], sFilled[i])
revSummary.rows[ent][k] = Σ 소속 사이트 rev.diff  (agg 사업장 제외, ent 기준)
revSummary.dom/ovs/seg  = 같은 방식으로 reg·seg2별
summary.rows[ent][k]    = Σ 실측(sFilled=None) s.bal   (agg 제외, 원문 표 법인 기준)
total                   = Σ 법인 rows
```

**`rev.src`는 두 칸 중 더 추정적인 쪽**을 쓴다 — 증분이 `cmp[k−1]`과 `cmp[k]` 양쪽에서 나오기 때문이다.
우선순위(강한 추정 → 약한): `fcst > bcst > interp > p8 > xi1 > 실측`. 7사 임베드 데이터 전수 대조로 역산했다
(예: `(interp, p8)` → `interp`, `(p8, fcst)` → `fcst`).

**`summary.src[ent][k]`가 산출 방식을 지시한다:**

| src 값 | 처리 |
|---|---|
| `명시+기타(계산)` | 사이트 실측 `bal` 합 (+ 원문 '기타' 행 — v1 미반영) |
| `공시총계`·`공시총계(단일)` | 회사 공시 총계. 사이트 합이 아니므로 **손대지 않는다**(현대건설) |
| `""`(빈 문자열) | 그 분기 **집계 대상 아님**. `rows`는 `None`으로 남겨야 한다 |

**집계 귀속 법인은 `sites[].ent`(정규화 라벨)가 아니라 그 분기 원문 표의 법인**이다.
표 앞 문맥의 앵커(`1) 현대건설`, `2) 자이에스앤디`)로 판정하고, 못 읽으면 원래 라벨을 쓰되
그 법인이 이번 분기 비집계(`src=''`)면 집계 대상 대표 법인으로 넘긴다 — GS이니마 사업장이
2025Q1 표 개편 후 GS건설 표에 실려 GS건설로 집계되는 실제 케이스(18.5조 규모)가 이 규칙으로 재현된다.

`revSummary`도 같은 축을 쓰되 **이번 분기 표에 없는 사업장은 직전 표시법인을 승계**한다(`_disp_ent`).
승계가 없으면 2025Q1에 GS건설로 옮겨졌지만 이번 분기 표에서 빠진 사업장이 원래 라벨로
되돌아가 매출이 엉뚱한 법인으로 간다(GS이니마 52,666). 표시법인이 바뀌면 `ev`에
`{"f":"표시법인"}` 이벤트를 남겨 다음 분기의 승계 근거로 삼는다.
7사 전 분기 대조로 확인했고, DL이앤씨의 독립 사례(DLE-2-0074의 2023Q2 이관)도 이 규칙으로 맞는다.

**국내/해외 소계(`dom`/`ovs`)는 사이트의 정적 `reg`가 아니라 그 분기 원문이 명시하는 구분**을 따른다:

| 신호 | 회사 | 처리 |
|---|---|---|
| 표가 `[국내공사]`/`[해외공사]`로 분할 | GS건설 | 표 lead의 표지(꼬리 200자만 본다 — 본문의 '해외종속회사' 같은 낱말에 오판하지 않도록) |
| 발주처 열의 `(국가)` 접두 | 삼성물산 | `(한국)`이면 국내, 그 외 국가면 해외. `(주)`·`(유)` 등 법인격 괄호는 국가가 아니다 |
| 신호 없음 | HDC현산 | 전 분기 `ovs=0`이면 회사가 해외를 분리 공시하지 않는 것 — 전액 국내 |

삼성물산은 시공지가 해외인데 발주처가 한국 법인인 원전 수출 3건(루마니아 1호기·CTRF·UAE 원전,
합계 148,706)이 이 규칙으로 국내에 잡힌다. `revSummary.dom/ovs`는 반대로 **정적 `reg` 기준**이 맞다.

집계 결과는 `int`로 정규화한다(파이썬 합산이 `1725578.0`을 만들면 원본과 타입이 달라진다).

### 3.7 예측(`fcst`) — 기본 비활성

마지막 실측 분기를 앵커로, `assets/curve_D.json`(지역×공종 경험 분위수 p50)을 리베이스한다:

```
x(k)   = (분기말(k) − 착공일) / (완공예정일 − 착공일)        # 공기 경과율
delta  = pr[앵커] − p50(x(앵커))                            # 이 현장의 곡선 대비 편차
pr(k)  = clamp(p50(x(k)) + delta, 0, 100),  단 pr[앵커] 이상(단조 증가 강제)
cmp(k) = round(amt × pr(k) / 100);  bal(k) = amt − cmp(k);  sFilled(k) = 'fcst'
```

**`--forecast` 플래그를 줘야만 동작한다(기본 off).** 원 빌더가 *어느 사업장을 어디까지* 예측하는지의
중단 조건이 완전히 역산되지 않았고, 우리 쪽이 과잉 생성하기 때문이다 — 대우건설 2026Q2 재적재에서
원본은 354개 중 160개만 미래 4분기를 채우는데(마지막 실측이 오래된 장기 미보고 현장은 비워 둔다)
우리 로직은 전부 채웠다. 잘못된 미래 수치를 새로 만드는 것보다 기존 예측을 보존하는 편이 안전하다.
축이 밀려도 예측 셀은 분기 라벨 기준으로 따라가고, 실측이 들어오면 그 칸만 덮인다.

곡선 자체의 재적합(7사 실측 풀링 → 분위수 재계산)도 미구현이며 2026-08 시점 곡선을 고정 사용한다.
**backtest가 보여주듯 진행률 80% 이상 구간에서 +74% 과대예측 편향이 있으므로**, 예측값은
보전 표시(`fcst`)로만 쓰고 실측처럼 다루면 안 된다.

### 3.8 검증과 fail-closed

`_validate()`가 통과해야만 파일을 쓴다:
- `fqF[:len(fq)] == fq`, `len(fqF) == len(fq) + 4`
- 전 사이트 시계열 배열 길이 == `len(fqF)`
- 전 분기 `summary.total == Σ 법인 rows`
- `json.dumps(D)` 직렬화 가능

쓰기는 `inject_data()` → `atomic_write()`(tmp + `os.replace`). 주입 전 JSON 라운드트립을 한 번 더 검증한다.
파서가 미지 헤더를 보고하면 그 시점에 예외를 던지고 **파일을 건드리지 않는다**.

재적재는 멱등이다 — 같은 분기를 다시 빌드하면 값이 동일하게 재현된다(`tests/test_build.py`).

### 3.9 파생 페이지 재생성 (`kce_render.py`)

`--apply` 시 `matrix.html`·`trace.html`을 DATA에서 다시 만든다. 두 페이지는 빌드타임
프리렌더라 DATA만 갱신하면 옛 데이터가 남기 때문이다.

**정합성 근거: 재생성 결과가 현재 저장된 원본과 바이트 단위로 동일하다(7사 전부).**
matrix는 2,235 사업장 × 23분기의 값·셀 클래스·툴팁 문구·`data-*` 속성까지 일치하고,
trace는 SITES 배열이 완전히 같다. 즉 렌더 규칙이 원 빌더와 동치다(`tests/test_render.py`).

역산해서 맞춘 세부 규칙:
- `data-v`는 `%g` 포맷(유효숫자 6) — `1003131` → `1.00313e+06`
- 라벨의 법인 접두는 **관계사 배지가 붙는 행에서만 생략**(배지가 폭을 먹어 공사명이 잘림).
  배지 없는 행은 `<b>법인</b> · 공사명`, title에는 항상 법인 유지
- 이스케이프는 `&`·`<`·`>`에 더해 `'` → `&#39;`(속성값 안전). 실제 산출물에 쓰인 엔티티는 `&amp;`와 `&#39;` 둘뿐
- matrix 범례는 5종뿐 — `xi1`(XI-1 교차참조 확정값)은 원문 확정값이라 **테두리 없이** 실측처럼 그린다
  (index.html 상세표에서만 민트 점선 `.flx`로 구분)
- trace는 그룹 순서가 아니라 **사업장 코드 숫자 순** 정렬. r3는 `p8Full.품목 · 발주처`,
  r11은 `xipFull.계약명 · 계약상대방` 결합 문자열

```bash

cd argus/kce/tools
for CO in sct hec sea dwe gse dle ipark; do

```

dry-run 리포트에서 반드시 확인할 것:
- `created` — 신규 사업장. 회사가 표를 재편했을 때 기존 사업장이 신규로 잘못 잡힐 수 있다.
- `disappeared` — 직전 분기 실측이었는데 이번에 사라진 사업장. 준공이면 정상, 아니면 표 분할 누락 의심.
- `p8_unmatched` — III-8에만 있는 이름. 사업장 미생성 상태다.
- `agg_rows` — 합계·기타 행으로 걸러낸 수. 갑자기 늘면 파서가 개별 행을 집계로 오인한 것.

이 레포(phalanx)의 `AGENTS.md` 규약상 `tools/` 아래 새 파일은 자유롭게 만들 수 있고,
크론이 덮어쓰는 대상이 아니다. `argus/kce/` 전체가 새 디렉토리이므로 빌더 충돌은 없다.

## 5. coRev(실제 매출) 갱신 사양 — 미구현

`coRev.src`가 산출 방법을 그대로 기록해 두었다: `"분기보고서(2022.05.16)+반기보고서(2022.08.16) 차분"`.
즉 **누적 공시를 직전 보고서와 차분**해 분기값을 만든다.

- `con`/`sep` = 연결/별도 손익계산서 매출액. 반기 누적 − 1분기 = 2분기.
- `i4*` = II-4 「매출 및 수주상황」의 **매출실적 표**(부문·매출유형·품목 × 기수 열). 이미 `ii4` 절에 함께 들어온다.
  `i4_seg:X`(부문별), `i4_dom`/`i4_ovs`(국내/해외), `i4_adj = i4 − Σ i4_seg`(연결조정 차액).
- 회사별 구성 차이는 `assets/revcfg_all.json`(원 사이트 `REVCFG` 7사분 전체)에 보존돼 있다 —
  어떤 계열을 어떤 라벨로 표시할지, 부문 어휘가 무엇인지가 여기 있다.
- 주의: 대우건설은 지역분해가 연결조정 전 기준(`i4 − (dom+ovs) = i4_adj`), HDC현산은 부분 분해라
  `i4 = dom + ovs`가 성립하지 않는다(LOGIC.md §3.6). 검증식을 회사별로 달리 둬야 한다.

## 6. XI-1 갱신 사양 — 미구현

`xip` = `{amt, supCur, supCum, recvCur, recvCum, cur, nm, mt}`. 두 원천이 있다:
1. **정기보고서 XI절** 「그 밖에 투자자 보호를 위하여 필요한 사항 - 나. 진행 현황」 —
   분기 축에 바로 얹을 수 있는 형태. 다만 2024Q4부터, 주로 반기·사업보고서에만 수록된다(「표 없음」이 정상).
2. **수시공시 단일판매ㆍ공급계약체결**(`publicType=I001`) — 계약 시점 이벤트. 정정공시 구조
   (`정정항목|정정전|정정후`)라 대장 관리가 필요하고, EUC-KR이다.

머리행 방언이 가장 심한 절이다: 신고일자 접미가 회사마다 `신고일자`/`(최초)`/`(최근)`/`(최종)`으로 갈리고,
단위가 한 표 안에서 `계약금액총액(원)` + `판매ㆍ공급금액(백만원)`으로 섞인다. `COL_ALIAS`에 xi_* 별칭을
넣어 두었으나 실표 대조는 아직이다. `mt`(매칭 상태)는 II-4 사업장과의 연결 판정 결과라 사람 확인이 필요하다.

## 10. 알려진 한계 (검증으로 확인, 미해결)

- **`summary.rows`가 `공시총계`인 법인(현대건설 4개 법인)은 새 분기에 비어 있다.** 그 값은
  회사가 공시한 총계라 사이트 합으로 대체할 수 없다. 가드가 사이트 합으로 덮는 것을 막고
  리포트에 남기지만, 원문 합계행을 읽어 채우는 경로는 v2 과제다.
- **`_expand_grid`는 "잘린 행 + 비인접 rowspan" 조합에서 열이 밀린다.** 실제 원문 393개 표를
  HTML 표준 슬롯 배치 참조 구현과 전수 대조했을 때 **차이 0건**이라 현재 데이터 오염은 없지만,
  합성 입력으로는 재현된다.
- **XI-1(`xip`)·`coRev`·`prC`는 갱신되지 않는다** — 경로는 정찰로 확인됐다(§5·§6).
- **상류 원본이 복제 이후 XI-1 렌더링을 추가했다**(`--xi` CSS 변수, 차트 `xi1` 분기).
  우리 복제본은 2026-08-31 스냅샷이다. 재복제 시 `kce_render`의 xi1 규칙(현재는 테두리 없음)을
  함께 갱신해야 바이트 동치가 유지된다.
